# AGENTS.md - AI Assistant Guide for UKRS2

## Project Overview

**UK Railway Set (UKRS2) - Community Bugfixes** is an OpenTTD NewGRF (Graphics Replacement File) providing British railway vehicles for the transport simulation game OpenTTD/TTDPatch.

- **Original Author**: David Dallaston (PikkaBird)
- **Bugfix Maintainer**: Mircea Chirea
- **Repository**: https://github.com/CMircea/UKRS2
- **Current Version**: 1.06
- **GRF ID**: `MCX` (prefix for both sets)
- **Codebase**: ~15,000 lines of hand-coded NFO (~2008)

## Understanding NFO

**NFO is serialized structs in hex, not a programming language.**

- Code reuse = copy/paste mostly
- VarAction2 chains = logic/control flow
- Variable 7E = procedure calls (call another VarAction2 chain)
- Variable 7D = temporary registers (store/retrieve computed values)

## File Formats

### NFO Files (`.nfo`)
- **Low-level NewGRF source format** - assembly-like syntax
- Generated by decompiling GRF files using GRFCodec
- Contains sprite definitions, action blocks, and vehicle properties
- Line format: `spritenum * size [data]`

### GRF Files (`.grf`)
- **Compiled binary format** for OpenTTD/TTDPatch
- Created from NFO files using grfcodec
- Users install these files in their OpenTTD `newgrf` directory

## Development Workflow

### Required Tools
- **GRFCodec**: Compiles NFO to GRF and decompiles GRF to NFO
- **NFORenum**: Validates and formats NFO files (fixes sprite numbers, checks syntax)

Install on Debian/Ubuntu:
```bash
apt-get install grfcodec
```

### Build Commands

**Compile NFO to GRF:**
```bash
grfcodec -e ukrs2.grf
grfcodec -e ukrs2-addon.grf
```

**Decompile GRF to NFO:**
```bash
grfcodec -d ukrs2.grf
grfcodec -d ukrs2-addon.grf
```

**Validate/format NFO files:**
```bash
nforenum ukrs2.nfo
nforenum ukrs2-addon.nfo
```

### Typical Edit Workflow
1. Edit the `.nfo` file(s)
2. Run `nforenum` to validate and fix sprite numbers
3. Run `grfcodec -e` to compile
4. Test in OpenTTD
5. Commit both `.nfo` and `.grf` files

### Finding Things in the NFO

A vehicle is defined across multiple actions that work together:

```
Action 0  → Define properties (speed, power, cost, vehicle ID)
Action 1  → Define sprite sets (the graphics)
Action 2  → Define sprite groups / VarAction2 chains (logic)
Action 3  → Link Action 2 to the vehicle ID from Action 0
Action 4  → Define the vehicle's name string
```

**Search tips:**
- **Find a vehicle by name**: Search for the quoted name string (e.g., `"Class 73"`)
- **Find Action 0 for vehicle ID xx**: Search for `00 00` followed by the ID bytes
- **Find Action 3 for vehicle ID xx**: Search for `03 00` followed by the ID
- **Find VarAction2 chains**: Search for `02 00` (Action 2 for trains)
- **Find railtype checks**: Search for `63` (var 63) or `4A` (deprecated var 4A)

**Vehicle IDs** in UKRS2 are assigned sequentially. The Action 8 sprite defines the GRF, then vehicles follow. Check Action 0 sprites for the `first-id` byte to find where each vehicle's definition starts.

**Sprite numbers** (leftmost column) are auto-fixed by nforenum - don't manually renumber them.

## NFO & NewGRF Specifications

### Action Types Overview

NewGRF modifications are organized around numbered "Actions":

| Action | Purpose | Description |
|--------|---------|-------------|
| **0** | Properties | Define vehicle/object properties (speed, power, cost, capacity) |
| **1** | Sprite Sets | Define one or more graphics sets |
| **2** | Sprite Groups | Define graphics set IDs; includes VarAction2 for computed results |
| **3** | Graphics Assignment | Associate Action 2 results with Action 0 items |
| **4** | Text Strings | Define custom text and names |
| **5** | Sprite Replacement | Replace TTD's built-in sprites |
| **6** | Parameter Modification | Modify bytes in following sprite |
| **7** | Conditional Skip (activation) | Skip sprites based on conditions during GRF activation |
| **8** | GRF Metadata | GRF ID, name, description, version |
| **9** | Conditional Skip (init) | Skip sprites during initialization AND activation |
| **10 (0A)** | Sprite Replacement | Replace specific TTD sprites by number |
| **11 (0B)** | Sound Effects | Import or define sound effects |
| **12 (0C)** | Font Glyphs | Load font characters |
| **13 (0D)** | String Translation | Translate default TTD strings |
| **14 (0E)** | Extended Info | Parameters UI, URL, versioning, palette info |

### Action 0 Format (Properties)

Action 0 defines properties for vehicles/objects. Byte format:

```
<sprite-num> * <length> 00 <feature> <num-props> <num-ids> <first-id> [<prop> <value>]...
```

**Example breakdown:**
```
9502 * 7     00 00 01 01 79 06 00
             │  │  │  │  │  │  └─ value: 00 (no climates = unavailable)
             │  │  │  │  │  └──── property: 06 (climate availability)
             │  │  │  │  └─────── first-id: 79 (vehicle ID)
             │  │  │  └────────── num-ids: 01 (1 vehicle)
             │  │  └───────────── num-props: 01 (1 property)
             │  └──────────────── feature: 00 (trains)
             └─────────────────── Action 0
```

**Common train properties:**
| Prop | Size | Description |
|------|------|-------------|
| 05 | B | Track type (index into railtype table) |
| 06 | B | Climate availability (bitmask: 01=temp, 02=arctic, 04=trop, 08=toyland) |
| 09 | W | Speed (mph × 1.6, or km/h × 1.0) |
| 0B | W | Power (hp) |
| 0D | B | Running cost factor |
| 14 | B | Weight (tons, low byte) |
| 1F | B | Tractive effort coefficient (0-255, 255=100%) |

### GRF Version

UKRS2 is **GRFv8** (requires OpenTTD 1.2+). Key implications:

- **All callbacks are 15-bit** - results use `xx 80` format (not legacy 0xFF?? handling)
- **Boolean callbacks need explicit 0 or 1** - not just "zero or non-zero"
- **No TTDPatch support** - OpenTTD only

The GRF version is declared in Action 8.

### NFO Escape Sequences

Use escape sequences instead of raw hex for readability. Prefer these in new code and when updating existing code.

**Data escapes:**
| Escape | Meaning | Example |
|--------|---------|---------|
| `\b<dec>` | Byte from decimal | `\b255` → `FF` |
| `\b*<dec>` | Extended byte (FF prefix for values >FE) | `\b*300` → `FF 2C 01` |
| `\w<dec>` | Word from decimal (little-endian) | `\w1000` → `E8 03` |
| `\wx<hex>` | Word from big-endian hex | `\wxABCD` → `CD AB` |
| `\d<dec>` | Dword from decimal | `\d100000` → `A0 86 01 00` |
| `\dx<hex>` | Dword from big-endian hex | `\dx12345678` → `78 56 34 12` |
| `\w<date>` | Word from date (days since 1920) | `\w1990-01-01` |
| `\d<date>` | Dword from date | `\d2050/06/15` |

**String escapes:**
| Escape | Meaning |
|--------|---------|
| `\\` | Literal backslash |
| `\n` | Newline |
| `\"` | Literal quote |
| `\xx` | Byte from hex (1-2 chars) |

**Action-specific escapes** follow the pattern `\<action><operator>`:
- `\2+`, `\2-`, `\2*` etc. for VarAction2 operators (see operator table)
- `\7GG` for Action 7 "GRF is active" condition
- Check each action's spec page for available escapes

**Byte ordering** - NFO uses little-endian:
```
Decimal 1000 as word:
  1000 = 0x03E8 → pad to 4 digits → split: 03 E8 → reverse: E8 03
```

### VarAction2 (Variational Action 2)

VarAction2 enables computed decisions based on game state variables. It's a conditional switch that determines callback results or chains to another Action 2.

#### Byte Format

```
<Sprite-number> * <Length> 02 <feature> <set-id> <type> <variable> <varadjust> <nvar> (<set-id> <low-range> <high-range>){n} <default>
```

| Field | Size | Description |
|-------|------|-------------|
| `02` | 1 byte | Action 2 identifier |
| `feature` | 1 byte | Feature type (00=trains, 01=road vehicles, etc.) |
| `set-id` | 1 byte | ID for this VarAction2 (referenced by Action 3 or other Action 2s) |
| `type` | 1 byte | Variable access size and scope (see below) |
| `variable` | 1 byte | Variable number to read |
| `varadjust` | variable | Shift, mask, and optional operations |
| `nvar` | 1 byte | Number of ranges (0 = special: return raw value) |
| `set-id` | 2 bytes | Target Action 2 ID or special value (per range) |
| `low-range` | 1-4 bytes | Inclusive minimum (size matches type) |
| `high-range` | 1-4 bytes | Inclusive maximum (size matches type) |
| `default` | 2 bytes | Default Action 2 ID if no ranges match |

#### Type Byte Values

The type byte determines both **variable access size** and **object scope**:

| Type | Size | Scope | Description |
|------|------|-------|-------------|
| **81** | Byte | Self | Read byte from current vehicle |
| **82** | Byte | Related | Read byte from related object (lead vehicle in consist) |
| **85** | Byte | Self | Advanced VarAction2 with operators |
| **86** | Byte | Related | Advanced VarAction2 on related object |
| **89** | DWord | Self | Read dword from current vehicle |
| **8A** | DWord | Related | Read dword from related object |

**Note**: Types 81/85 read from the current vehicle; 82/86 read from the lead vehicle of the consist.

#### Variable Ranges

| Range | Description |
|-------|-------------|
| **00-3F** | Global variables (feature-independent) |
| **40-5F** | Feature-specific calculated variables |
| **60-7F** | "60+x variables" - require an extra parameter byte after the variable number |
| **80-FF** | "80+x variables" - direct memory offsets into game structures |

#### varadjust Field Format

```
<shift-num> <and-mask> [<add-val> <divide-val>/<modulo-val>]
```

**shift-num bits**:
| Bit | Meaning |
|-----|---------|
| 0-4 | Right-shift amount (0-31) |
| 5 (0x20) | Advanced VarAction2 flag - another operator/variable follows |
| 6 (0x40) | Enable shift-and-add-divide |
| 7 (0x80) | Enable shift-and-add-modulo |

#### Special Set-ID Values (in ranges)

| Value | Meaning |
|-------|---------|
| **8000-FEFF** | Return as callback result (value = set-id - 0x8000) |
| **7FFE** | Return calculated value directly as callback result |
| **7FFF** | Signal callback failure |

#### nvar=0 Special Case

When `nvar=0`, the VarAction2 returns the raw calculated value with bit 15 set. Useful for multi-value callbacks.

### Vehicle Variables (40-7F)

#### Standard Vehicle Variables

| Var | Size | Description | Notes |
|-----|------|-------------|-------|
| **40** | D | Position in consist: `00nnbbff` | ff=position, bb=from end, nn=total count |
| **41** | D | Position among same vehicle ID | Same format as 40 |
| **42** | D | Consist cargo info: `uuiicctt` | tt=common cargo, cc=classes, ii=count, uu=refit |
| **43** | D | Player info | Number, type, colors |
| **45** | D | Curvature info | Between wagon pairs |
| **46** | D | Motion counter | 1/4096 tile units moved |
| **47** | D | Vehicle cargo info | Current vehicle's cargo details |
| **4A** | D | **Current railtype** (DEPRECATED) | See warning below |
| **4D** | D | Position in articulated vehicle | For multi-part vehicles |

| Var | Size | Description | Parameter |
|-----|------|-------------|-----------|
| **60** | D | Count specific cargo in consist | Cargo type |

| Var | Description |
|-----|-------------|

### Variable 4A vs 63 (Railtype Detection)

**IMPORTANT**: Variable 4A is deprecated and unreliable.

#### Variable 4A (DEPRECATED)
- Returns: `xxxxFFrr` where `rr` is the numeric railtype index
- **Problem**: Index values are inconsistent across different GRF combinations
- The index depends on load order and which GRFs define railtypes

#### Variable 63 (OpenTTD 1.11+)
- **Parameter**: Index into the vehicle's railtype translation table
- Returns bit flags indicating compatibility and power status

**Variable 63 Return Value Bits**:
| Bit | Meaning |
|-----|---------|
| 0 | NewGRF knows the queried railtype |
| 1 | Vehicle is **compatible** with current tile's track |
| 2 | Vehicle is **powered** on current tile |
| 3 | Queried type exactly matches current tile's type |

**Usage**: Test bit 2 (mask with `04`) to check if vehicle has power.

```nfo
// Example: Check if powered on ELRL (assuming ELRL is index 01 in railtype table)
81 63 01 04 ...  // var 63, param=01, mask=04 (bit 2)
// Result: 04 = powered, 00 = not powered
```

Source: [OpenTTD PR #8554](https://github.com/OpenTTD/OpenTTD/pull/8554)

### VarAction2 Advanced Operators

For type 85/86/89/8A VarAction2, multiple variables can be chained with operators using the accumulator model.

#### Format
```
<Sprite> * <Length> 02 <feature> <set-id> <type> <variable> <varadjust> [<operator> <variable> <varadjust>]... <nvar>
```

Set bit 5 (0x20) in shift-num to indicate another operator/variable/varadjust follows.

#### Operator Codes

| Code | Escape | Operation | Type |
|------|--------|-----------|------|
| 00 | `\2+` | Add | Signed |
| 01 | `\2-` | Subtract | Signed |
| 02 | `\2<` | Minimum | Signed |
| 03 | `\2>` | Maximum | Signed |
| 04 | `\2u<` | Minimum | Unsigned |
| 05 | `\2u>` | Maximum | Unsigned |
| 06 | `\2/` | Divide | Signed |
| 07 | `\2%` | Modulo | Signed |
| 08 | `\2u/` | Divide | Unsigned |
| 09 | `\2u%` | Modulo | Unsigned |
| 0A | `\2*` | Multiply | Both (truncated to 32 bits) |
| 0B | `\2&` | Bitwise AND | — |
| 0C | `\2\|` | Bitwise OR | — |
| 0D | `\2^` | Bitwise XOR | — |
| 0E | `\2s` or `\2sto` | Store to var 7D: `7D[val2] = val1`, returns val1 | — |
| 0F | `\2r` | Return val2 (discards val1) | — |
| 10 | `\2psto` | Store to persistent var 7C | — |
| 11 | `\2ror` | Rotate right 32-bit | — |
| 12 | `\2cmp` | Signed compare: 0 if =, 1 if val1 < val2, 2 if > | Signed |
| 13 | `\2ucmp` | Unsigned compare | Unsigned |
| 14 | `\2<<` | Left shift | — |
| 15 | `\2u>>` | Right shift | Unsigned |
| 16 | `\2>>` | Right shift | Signed |

#### Temporary Storage (var 7D)

256 registers (00-FF) for intermediate values within a VarAction2 chain:

```nfo
// Store accumulator to register 0x10
\2s 10   // or: operator 0E, followed by var 1A with mask 10 00 00 00

// Read register 0x10 into accumulator
7D 10    // Just read var 7D with parameter 10
```

#### Procedure Calls (var 7E)

Calls another VarAction2 chain as a subroutine:

```nfo
7E xx    // Call VarAction2 ID xx, its result becomes the variable value
```

- The called chain inherits the feature from the calling context
- Result is returned to the accumulator
- Using nvar=0 in the called chain returns a 15-bit value; use var 1C to get full 32 bits

### Action 7/9 (Conditional Skip)

Skip sprites based on conditions. Action 7 executes during activation; Action 9 executes during initialization AND activation.

#### Format
```
<sprite-number> * <length> 07 <variable> <varsize> <condition-type> <value> <num-sprites>
```

| Field | Size | Description |
|-------|------|-------------|
| `07` or `09` | 1 byte | Action type |
| `variable` | 1 byte | Variable to test (00-7F = GRF params, 80+ = global vars) |
| `varsize` | 1 byte | Size of variable (01, 02, or 04 bytes) |
| `condition-type` | 1 byte | Test type (see below) |
| `value` | varsize | Comparison value |
| `num-sprites` | 1 byte | Sprites to skip (00 = skip rest of file) |

#### Condition Types

| Type | Description |
|------|-------------|
| **00** | Bit is set in variable |
| **01** | Bit is clear in variable |
| **02** | Variable equals value |
| **03** | Variable does NOT equal value |
| **04** | Variable < value |
| **05** | Variable > value |
| **06** | GRFID is active |
| **07** | GRFID is NOT active |
| **08** | GRFID has been initialized (set up Action 8) |
| **09** | GRFID has NOT been initialized |
| **0A** | Cargo type is available |
| **0B** | Cargo type is NOT available |
| **0C** | Railtype label is defined |
| **0D** | Railtype label is NOT defined |

#### Example: Version Check

```nfo
// Skip if OpenTTD version < 1.11 (where var 63 was added)
47 * 6 07 9D 04 05 00 00 00 01 nn
// 9D = platform version variable
// 04 = dword size
// 05 = greater than condition
// value = version number
// nn = sprites to skip
```

#### If/Else-If Patterns with Action 7

Action 7 implements if/else-if logic for **load-time** decisions: version checks, parameter handling, and **tracktype property fallbacks**.

**Key techniques**:
- **Action 10** (`10 xx`) defines a label (00-FF) that Action 7 can jump to
- **Variable 9A** enables unconditional jumps (always true, for "else" branches)
- **Duplicate labels** jump to the first matching label *that follows* (useful for reusing label numbers)
- **Prefer negative logic** (test if false, skip block) over positive logic:
  - Fewer labels needed
  - Safer (no accidental backward jumps)
  - Easier to maintain
  - Linear flow
- Reserve positive logic for very complex branching where blocks are shared, or when optimizing for code space

**OR chain** (simple - all conditions → same destination):
```nfo
// if (A || B || C) → skip to label, else → do something
    * 07 00 04 0E "3RDC" 55    // if 3RDC defined → label 55
    * 07 00 04 0E "SAAZ" 55    // if SAAZ defined → label 55
    * 07 00 04 0E "3RDR" 55    // if 3RDR defined → label 55
    <Action 0: disable vehicle>  // none matched - disable
    * 10 55                      // label 55: continue
```
No var 9A needed - all paths go to the same place.

**If-else-if** (complex - different actions per condition):

**Tracktype Fallback Pattern** (for Action 0 property 05):
```nfo
// if 3RDC defined → use 3RDC
// else if SAAZ defined → use SAAZ
// else → use ELRL

// Check: is 3RDC NOT defined? Jump to label 01
    * 07 00      // Action7, variable (ignored for railtype check)
         04      // varsize = 4 (required for railtype labels)
         0D      // condition: railtype NOT defined
         "3RDC"  // railtype label to check
         01      // jump to label 01

// 3RDC is defined - use it
    <Action 0: set tracktype to "3RDC">

// Unconditional jump to end (label 03)
    * 07 9A      // variable 9A (for unconditional jump)
         01      // varsize = 1
         00      // condition: bit set
         00      // value: bit 0
         03      // jump to label 03

// Label 01: check SAAZ
    * 10 01

// Check: is SAAZ NOT defined? Jump to label 02
    * 07 00 04 0D "SAAZ" 02

// SAAZ is defined - use it
    <Action 0: set tracktype to "SAAZ">

// Unconditional jump to end
    * 07 9A 01 00 00 03

// Label 02: ELRL fallback
    * 10 02
    <Action 0: set tracktype to "ELRL">

// Label 03: end
    * 10 03
```

**When to use what:**
- **Action 7 fallbacks**: Setting *which railtype a train uses* (Action 0 property 05) - load-time decision based on what railtypes exist
- **Var 63 in VarAction2**: Detecting *what rail the train is currently on* at runtime to adjust power/speed dynamically

### Callbacks

Callbacks are special Action 2 chains that OpenTTD "calls" to dynamically modify features. The game sets variable 0C to the callback number, then follows the vehicle's Action 3 entry through VarAction2 chains to get a result.

#### How Callbacks Work

1. OpenTTD triggers a callback by setting variable **0C** to the callback number
2. Your VarAction2 chain checks var 0C and branches accordingly
3. Return a **callback result** by setting bit 15 (0x8000) in the set-id
4. Unknown callbacks **must** fall through to normal graphics (safety requirement)

#### Implementation Steps

1. **Enable the callback** via Action 0 property bits (props 12, 14, 17, or 1E depending on callback)
2. **Set default values** for the property being modified in Action 0
3. **Define Action 3** for the vehicle if not already present
4. **Add VarAction2** checking callback variable 0C
5. **Access 0C as a word** (2 bytes) even for callback IDs < 0xFF
6. **Return callback results** with bit 15 set; regular set-ids for graphics
7. **Route unknown callbacks** to regular graphics as fallback

#### Callback Result Format

In GRFv8+, callback results use 15-bit values:
- `00 80` to `FF 80` = callback results 0x00 to 0xFF
- `xx 8y` where y > 0 = callback result 0xYxx (e.g., `34 81` = 0x134)
- **7FFE** = return calculated value directly as callback result
- **7FFF** = callback failed (use default behavior)

**Critical**: The last Action 2 in a callback chain must return a set-id with bit 15 set. This is invalid for regular graphics, so the chain must distinguish callback mode from graphics mode.

#### Key Vehicle Callbacks

| CB# | Hex | Name | Description |
|-----|-----|------|-------------|
| 16 | 0x10 | **Visual Effect** | Determine visual effect and wagon power status |
| 21 | 0x15 | **Refitted Capacity** | Return capacity after refit (up to 32,511) |
| 22 | 0x16 | **Articulated Parts** | Build multi-vehicle units (return part IDs, 7FFF to end) |
| 35 | 0x23 | **Purchase Text** | Additional text in purchase menu (return D0xx text ID) |
| 51 | 0x33 | **Sound Effect** | Custom sound effects (var 10 = event type) |
| 54 | 0x36 | **Change Properties** | Dynamically modify speed, power, weight, capacity |

#### Callback 36 (Change Properties)

Particularly important for dual-mode locomotives. Allows changing:
- Speed (property 09)
- Power (property 0B)
- Weight (property 14)
- Tractive effort (property 1F)

Variable **10** contains the property number being queried. Return the new value, or return **7FFF** (callback failure) to use the default property value.

#### Callback 16 (Articulated Parts)

Builds multi-vehicle units like locomotives with tenders or EMUs:
- Called repeatedly with variable **10** containing the part index (1, 2, 3...)
- Return the vehicle ID for each part
- Return **7FFF** to signal no more parts

#### Implementing Callbacks in VarAction2

```nfo
// Pattern: Check callback number (var 0C) and branch
// The VarAction2 chain starts from Action 3
// Note: set-ids like A0, A1, A2 are single-byte hex IDs you assign

// VarAction2 to dispatch callbacks (set-id A0)
1234 * 14    02 00 A0 85              // Action 2, trains, set-id=A0, type 85
             0C 00 FF FF              // var 0C, shift 0, mask FFFF (word!)
             02                       // 2 ranges
             A1 00 10 00 10 00        // callback 0x10 → set-id A1
             A2 00 36 00 36 00        // callback 0x36 → set-id A2
             A3 00                    // default → set-id A3 (graphics)

// Callback 10 handler (set-id A1) - returns visual effect
1235 * 10    02 00 A1 81              // Action 2, trains, set-id=A1, type 81
             variable 00 FF           // check some variable
             01                       // 1 range
             00 80 00 00              // return 0x00 (bit 15 set = callback result)
             40 80                    // default: return 0x40
```

**Key points:**
- Set-ids (A0, A1, A2...) are hex bytes you assign - used to chain Action 2s together
- Callback results have bit 15 set: `xx 80` returns value `xx`
- Always access var 0C as word (`FF FF` mask) even for callbacks < 0xFF

### Rail Types

#### Railtype Properties (Action 0, Feature 10)

| Prop | Ver | Size | Description |
|------|-----|------|-------------|
| 08 | 1.0 | 4*B | Railtype label (4-letter identifier) |
| 0E | 1.0 | B n*D | Compatible railtype list (vehicles can run) |
| 0F | 1.0 | B n*D | Powered railtype list (vehicles have power) |
| 10 | 1.0 | B | Flags (see below) |
| 14 | 1.0 | W | Speed limit (mph × 1.6) |
| 17 | 1.1 | D | Introduction date |
| 1D | 1.2 | B n*D | Alternate labels (for compatibility) |

**Railtype Flags (Property 10)**:
| Bit | Value | Description |
|-----|-------|-------------|
| 0 | 0x01 | Draw catenary sprites |
| 1 | 0x02 | Disallow level crossings |
| 2 | 0x04 | Hide from construction menu |
| 4 | 0x10 | Allow 90-degree turns |
| 5 | 0x20 | Disallow 90-degree turns (overrides bit 4) |

#### Reserved Labels

These cannot be undefined - the game always adds them if vehicles use those types:
- **RAIL** - Normal unelectrified rail
- **ELRL** - Electrified rail (catenary)
- **MONO** - Monorail
- **MGLV** - Maglev

### Standardized Railtype Scheme

A four-character label system enabling mix-and-match of track and vehicle sets.

#### Label Format: `[Gauge][Speed][Axle][Power]`

**Position 1 - Track Type/Gauge**:
| Code | Meaning |
|------|---------|
| S | Standard gauge |
| B | Broad gauge |
| N | Narrow gauge |
| n | Secondary narrow gauge |
| D | Dual standard/broad |
| d | Dual standard/narrow |
| M | Monorail |
| L | Maglev |

**Position 2 - Speed Class**:
Train sets should always use **A**. Track sets can use A through F for increasing speed limits.

**Position 3 - Axle Load**:
| Code | Meaning |
|------|---------|
| A | Low axle load |
| B | Medium-low |
| C | Medium |
| D | Medium-high |
| E | High axle load |

**Position 4 - Electrification**:
| Code | Meaning | Fallback |
|------|---------|----------|
| N | No electrification | — |
| E | Overhead catenary | — |
| 3 | Third rail | — |
| D | DC catenary | E |
| A | AC catenary | E |
| 4 | Fourth rail | 3 |
| Z | Third rail + catenary | 3 or E |
| Y | Fourth rail + catenary | 4 or E |

#### Common Labels for UKRS2

| Label | Meaning |
|-------|---------|
| `RAIL` | Standard unelectrified (maps to SAAN) |
| `ELRL` | Standard + overhead catenary (maps to SAAE) |
| `3RDR` | Third rail only |
| `3RDC` | Third rail + overhead catenary |

**NFO Note**: Labels starting with digits (like `3RDR`) must be written as string literals in the NFO:
```nfo
"3RDR"  // Correct
33 52 44 52  // Also correct (ASCII hex)
```

## Known Issues

### Dual-Mode Locomotive Bugs
Dual-mode locos (Class 73, Eurostar, A-Train, Class 92) have railtype detection bugs. The code uses deprecated variable 4A for railtype checks.

**Affected vehicles**: Any locomotive that changes behavior based on electrification (adjusts power, speed, or visual appearance when on electrified vs non-electrified track).

**The problem**: Variable 4A returns a numeric railtype index that's inconsistent across different games/GRF combinations. The index depends on which GRFs define which railtypes and in what order.

**Fix approach**:
1. Replace var 4A checks with var 63
2. Var 63 parameter = index into railtype translation table (e.g., index for `ELRL`)
3. Test bit 2 of result (mask with 04) to check if vehicle is powered
4. Add Action 7/9 version check to maintain compatibility with older OpenTTD

**Example pattern**:
```nfo
// Old (broken): Check if railtype index == some value
81 4A 00 FF ...  // var 4A returns inconsistent index

// New (correct): Check if powered on ELRL-type track
// Assuming ELRL is at index 01 in railtype table
81 63 01 04 ...  // var 63, param=01 (ELRL index), mask=04 (bit 2)
// Result: 04 = powered, 00 = not powered
```

See [OpenTTD PR #7000](https://github.com/OpenTTD/OpenTTD/pull/7000) for original discussion.

## Conventions for AI Assistants

### DO
- Run `nforenum` after editing NFO files to validate syntax
- Commit both `.nfo` and `.grf` files together
- Update version numbers in both NFO files when releasing
- Test GRF files in OpenTTD after changes
- Keep changes minimal and focused on bugfixes
- **Add visual byte breakdowns** when writing or updating complex NFO (VarAction2 chains, Action 7 conditionals, callbacks) - the hex is unreadable without annotations:
  ```
  1234 * 14    02 00 A0 85 0C 00 FF FF 01 A1 00 10 00 10 00 A2 00
               │  │  │  │  │  │  └──┴─ mask: FFFF (word)
               │  │  │  │  │  └────── shift: 00
               │  │  │  │  └───────── variable: 0C (callback number)
               │  │  │  └──────────── type: 85 (byte, self, advanced)
               │  │  └─────────────── set-id: A0
               │  └──────────────────  feature: 00 (trains)
               └───────────────────── Action 2
  ```

### DON'T
- Modify the GRF files directly (always edit NFO source)
- Change the GRF ID without coordination
- Add new vehicles (out of scope for bugfix repository)
- Ignore nforenum warnings (fix them or understand why they're acceptable)

### Commit Message Style
Based on history, use imperative mood describing the fix:
```
Fix dual 3rd rail & catenary trains not running at full speed/power under catenary.
Update VarAction2 with correct railtype indexes for overhead catenary
Run nforenum.
```
